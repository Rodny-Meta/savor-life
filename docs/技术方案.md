## 1. 登录体系：Redis token 会话 + 双拦截器（2026-09-26/27）

**流程**：验证码（TTL 2min）→ 手机号登录 → 随机 token 存 Redis（TTL 25 天，活跃即刷新=滑动过期）→ 前端 sessionStorage 携带 → 双拦截器校验。

| 拦截器 | order | 拦截路径 | 职责 |
|---|---|---|---|
| RefreshTokenInterceptor | 0 | /** | 刷新 token TTL、用户信息存 ThreadLocal、**永远放行** |
| LoginInterceptor | 1 | 需登录路径 | 无有效登录态返回 401 |

- ThreadLocal 清理放第一层 afterCompletion（线程池复用防串号）
- 选型理由：token 无状态可水平扩展（对比 Session）；安全性依赖 token 随机不可猜 + 登出即焚，TTL 长短非核心风险

## 4. 商铺缓存（2026-10-08 起，逐步加固）

### 4.1 基础：旁路模式 Cache Aside（2026-10-08）

- 读：查 Redis → miss 查库 → 回填（TTL 30min）
- 写：**先更新数据库，再删缓存**
- 实测：详情 764ms→14ms（54倍）

### 4.2 击穿防护方案一：互斥锁（当前主方案，2026-10-09）

`CacheClient.queryWithMutex` 执行流：

```
miss → SETNX 抢锁（setIfAbsent key "1" 10s，一条原子命令=加锁+过期兜底，无死锁窗口）
  ├─ 抢到：双检缓存 → 查库 → 回填 → 释放锁
  └─ 没抢到：休眠 50ms → 重查缓存 → 命中返回；未命中继续抢
```

- 特点：**一致性较好**（重建完成前拿不到新数据），代价是等待
- 死锁防护：锁自带 10s 过期，即使服务宕机锁也自动释放（对应笔记"expire 兜底"）

### 4.3 击穿防护方案二：逻辑过期（对比方案，2026-10-09）

`CacheClient.queryWithLogicalExpire`，key 永不过期，value = `RedisData{data, expireTime}`：

```
查询 → key 不存在 → 返回 null（此方案依赖预热，正常不会 miss）
     → 未过期 → 直接返回
     → 已过期 → 抢锁成功：线程池异步重建（新 expireTime=now+30min）
                抢锁失败：说明别人在重建
     → 当前请求一律返回旧值
```

- 特点：**可用性优先**（永不让请求等待），代价是短期不一致 + 内存常驻 + 需预热
- 项目内落点：独立 key 前缀 `cache:shop:logic:` + 预热端点 `POST /shop/preheat/{id}?expire=秒`
- 实测：预热(expire=30s) → 未过期查询 200 → 过期后查询 200（旧值）→ 3s 后 expireTime 更新（异步重建完成）

### 4.4 穿透防护：空值缓存（2026-10-09）

库中不存在 → 缓存 `""`（TTL 2min，`CACHE_NULL_TTL`）→ 同 key 后续请求被空值拦截。

- 实测：查 9999 → Redis 出现 `cache:shop:9999=""` TTL=120s，二查 18ms 不打库
- **布隆过滤器：暂不引入**。理由：本项目商铺 id 是少量固定数据、请求 id 来自页面链接非用户任意输入，空值缓存已够；布隆的误判率、不支持删除、额外维护成本（数据变更需重建过滤器）在此规模下收益为负。未来若开放 API / id 范围大 / 恶意流量多，再上 Redis 布隆模块（BF.ADD/BF.EXISTS）或 Guava BloomFilter
- 穿透方案全景（含今天笔记新增）：缓存空值（主力）/ 布隆过滤器 / ID复杂化（雪花，防枚举）/ ID校验（格式范围）/ 加强用户权限（限流）

### 4.5 通用缓存工具类：CacheClient（2026-10-09）

基于 StringRedisTemplate 封装，泛型 `<R, ID>` + `Function<ID, R> dbFallback`——工具只管缓存策略，"查什么库"由调用方注入：

| 方法 | 对应需求 | 能力 |
|---|---|---|
| `set(key, value, time, unit)` | 方法1 | 任意对象→JSON 存 string + TTL |
| `setWithLogicalExpire(...)` | 方法2 | +逻辑过期（防击穿方案二配套） |
| `queryWithPassThrough(...)` | 方法3 | 查询+反序列化+空值缓存（防穿透） |
| `queryWithLogicalExpire(...)` | 方法4 | 查询+逻辑过期（防击穿） |
| `queryWithMutex(...)` | 方法5（额外封装） | 互斥锁查询（防击穿+兼防穿透） |
| `tryLock / unLock` | — | 私有原语：SETNX+TTL 原子加锁 / DEL 释放 |

调用示例（ShopServiceImpl 一行完成防护查询）：

```java
return cacheClient.queryWithMutex(CACHE_SHOP_KEY, id, Shop.class, this::getById, CACHE_SHOP_TTL, TimeUnit.MINUTES);
```

### 4.6 缓存预热结论（2026-10-09）

| 方案 | 是否需要预热 | 原因 |
|---|---|---|
| 互斥锁 | **不需要** | miss 时可现场抢锁重建，冷启动自然回填 |
| 逻辑过期 | **必须预热** | key 永不过期依赖"提前写入"；miss 直接返回 null，方案失效 |

本项目需要预热的内容 = 采用逻辑过期方案的热点 key（商铺详情 id=1 等）。已提供 `POST /shop/preheat/{id}` 端点，生产上可由定时任务/发布脚本触发。类型列表 `cache:shop:type` 也适合发布时预热（启动即常驻）。

### 4.7 雪崩防护：TTL 加随机（2026-10-10，需求 2-2 收尾 ✅）

**根因**：大量 key 同一时刻集中创建、集中 TTL → 同一秒集体过期，瞬间的 miss 洪峰全部打向数据库。

**方案**：TTL 基础值 + 0~20% 随机偏移，把"同一秒的雪崩"摊薄成"一段时间内的零星 miss"。

| 位置 | 改动 | 效果 |
|---|---|---|
| `CacheClient.set()` | `time + RandomUtil.randomLong(0, Math.max(1, time/5))` | 所有走工具类的回填统一生效（如 30min → 30~36min） |
| `nullValueTtl()`（新增私有方法） | `CACHE_NULL_TTL + randomLong(0,2)` | 空值缓存 2~4min——空值也可能被批量制造（同时打一批不存在 id），同样要防雪崩 |
| `ShopTypeServiceImpl` | 回填改走 `cacheClient.set(...)` | 类型列表从"固定30min"纳入随机 TTL 体系 |

**验证**：同一批写入 4 个 key，TTL 实测 2099/1918/1858/2038（基础 1800s + 各不相同的随机偏移）✓；空值缓存 TTL 实测有随机浮动 ✓。至此缓存三防护齐备：**穿透 ✅（4.4）/ 击穿 ✅（4.2/4.3）/ 雪崩 ✅（4.7）**。

## 5. 全局ID生成器：RedisIdWorker（2026-10-09）

**解决**：自增 id 规律性太明显（可被遍历、窥探业务量）+ 单表数据量上限。

**64bit 结构**：

```
| 1bit 符号位（恒0） | 31bit 时间戳（相对2022-01-01 UTC的秒差，约69年） | 32bit 序列号（Redis自增，秒内上限2^32） |
```

- 序列号 key = `icr:{业务前缀}:{yyyyMMdd}`，**按天分段**：单 key 压力可控，且 key 的最终值天然是"当日发号量"统计器
- 特性对照：唯一性（Redis单线程自增）✓ 高可用（Redis主从+持久化）✓ 高性能（内存操作）✓ 递增性（时间戳+自增）✓ 安全性（无规律可猜）✓
- 实测：连发 5 个严格递增（646707716978376705~709）
- **接入位置**：优惠券秒杀订单号（阶段 2-3 使用 `nextId("order")`）；探店笔记也可用（对比当前数据库自增 id）
- **深化要点（2026-10-09 笔记消化）**：序列号是"当天累计值"非"每秒计数"（INCR 跨秒续涨、跨天换 Key 才重置）；按天分 Key 不是为了并发安全（INCR 本身原子），而是每日发号量统计 / 可过期清理 / 故障隔离；日期只占 Redis Key 字符串、不占 ID 任何一位；"Key 字符串拼接"与"ID 位运算拼装（ts<<32|seq）"是两件事。详见技术栈 Redis 14

## 6. JMeter 压测报告：互斥锁方案（2026-10-09）

- 环境：JMeter 5.6.3，100 线程 × 10 循环 = 1000 请求，直连后端 8081，压测前 `DEL cache:shop:1` 制造全 miss
- 脚本/报告：`backend/scripts/jmeter-shop-mutex.jmx` + `jmeter-report/`（HTML，可浏览器打开）

| 指标 | 值 | 解读 |
|---|---|---|
| 吞吐量 | **959.7 请求/秒** | 1 秒打完 1000 请求 |
| 平均响应 | 25ms | 绝大多数命中缓存 |
| 最大响应 | 246ms | 拿到锁重建缓存的那个请求（含查库） |
| 错误率 | **0.00%** | 1000 个请求全部成功 |

**互斥锁生效证据（后端日志分析）**：

- 压测窗口内"拿到锁，开始重建缓存"INFO 日志 **仅 1 条**（线程 io-8081-exec-26）——100 并发只有 1 个线程查库重建
- "未拿到锁，休眠50ms重试"DEBUG 32 条——这 32 个线程休眠一轮后重查缓存即命中返回
- **数据库在整个压测过程中只被查询 1 次**（若无互斥锁，100 个线程会同时打库）
- 压测后 `EXISTS cache:shop:1` = 1（重建回填成功）

## 7. 疑难解答（2026-10-09 收件箱）

### 7.1 @Resource vs @Autowired

| 对比项 | @Resource | @Autowired |
|---|---|---|
| 匹配策略 | **默认按名称**（先按字段名找同名 bean，找不到再退回按类型） | **默认按类型**（byType） |
| 多候选时 | 用 `name` 属性显式指定：`@Resource(name="shopServiceImpl")` | 配 `@Qualifier("shopServiceImpl")` 或依赖 `@Primary` |
| 归属 | **JSR-250 标准**（Jakarta EE 规范，Spring 负责支持它，但不是 Spring 发明的） | **Spring Framework**（也不是 Spring Boot 的） |

- "名称可以自定义吗"：可以。①bean 侧：`@Service("myShopService")` 自定义 bean 名（默认是类名首字母小写）；②注入侧：`@Resource(name=...)` / `@Autowired + @Qualifier(...)`
- 实战建议：同类型只有一个实现时两者等价（本项目多数场景如此）；多实现/需要指定名称时，@Resource 少写一个注解更省事，@Autowired 是 Spring 全家桶更通用的选择
- 本项目现状：统一用 `jakarta.annotation.Resource`（Boot 3 迁移后 javax→jakarta）

### 7.2 为什么 tryLock 里 setIfAbsent 要带过期时间（对应笔记"expire 兜底"）

课程版分两步 `setnx` + `expire` 存在窗口：刚 setnx 完、expire 还没执行时服务宕机 → 锁永不过期 → 死锁。本项目用 `setIfAbsent(key, "1", 10, SECONDS)` **一条原子命令**同时完成加锁+设过期，从根本上消灭这个窗口。

## 9. 优惠券秒杀（2026-10-09 预案 → 2026-10-10 需求 8-12 全量实施 ✅）

> 9.1-9.3 为方案要点（学习沉淀），9.4-9.5 为实施实录与证据链。

### 9.1 超卖根因与锁策略演进

- 超卖根因：「查库存 → 判断充足 → 扣减」三步**非原子**，多线程在判断后插队扣减（1 张票卖 2 单）
- **悲观锁**（synchronized/Lock）：认为冲突一定会发生，操作前先加锁串行执行；细粒度控制是关键（一人一单只锁 userId，不锁全部用户）
- **乐观锁**（版本号/CAS）：认为冲突偶发，不加锁，提交时校验版本号（只比原来大 1 = 没人改过）；失败可**自旋重试**；写多冲突激烈用悲观，读多写少用乐观
- **集群下 synchronized 失效**：锁监视器只在单 JVM 内，多 Tomcat 各持一把"同代码不同对象"的锁 → 必须外置公共锁（Redis / ZooKeeper）

### 9.2 一人一单的实现要点

- 判断库存充足后按 userId 查订单，已存在则拒绝下单
- **锁粒度**：`userId` 粒度，所有用户共用一把锁 = 全串行，性能崩
- **事务与锁的坑**：内部加锁可能"事务未提交、锁已释放" → 把**整个事务方法**包进锁内；`this.` 调用不走代理 → 事务失效，需 `AopContext.currentProxy()` 拿原始代理对象调用
- 事务失效场景：①非 public 方法 ②非代理对象调用（this.）

### 9.3 Redis 分布式锁（防误删完整方案）

- 加锁：`SET lock:key UUID-线程ID NX EX 10s`（value 存线程标识）
- **误删问题一**：业务超时 > 锁 TTL，锁自动过期被 B 抢走，A 执行完 del 删了 B 的锁 → C 也进来，互斥失效。解法：存线程标识，释放前校验
- **误删问题二**：有标识但「GET 判断 + DEL」两步非原子——刚判断完锁恰好过期、别人抢走，DEL 还是删了别人的锁。解法：Lua 脚本把判断+删除打包成原子命令
- **Lua 传参与工程实践**：key 放 `KEYS` 数组、其他参数放 `ARGV` 数组；脚本文件放 `resources/lua/` 专门文件夹，避免 Java 硬编码
- 骨架：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

- 时序还原与对比总结详见技术栈 Redis 05（第五、六节）

### 9.5 实施要点与坑（面试可讲）

- **事务与锁的配合**：锁内用 `AopContext.currentProxy()` 调事务方法（启动类 `@EnableAspectJAutoProxy(exposeProxy = true)` + pom `spring-boot-starter-aop`），防"事务未提交、锁已释放"
- **锁粒度**：一人一单只锁 userId（`lock:order:{userId}`）；全用户一把锁 = 全串行灾难
- **Hutool UUID 包位置坑**：课程写法 `UUID.randomUUID().toString(true)` 是 Hutool `cn.hutool.core.lang.UUID` 的 API（**不在 core.util 包**，直接导入编译失败）；本项目改用 JDK 原生 `java.util.UUID.randomUUID().toString().replace("-","")` 等价实现
- **误删问题一/二的落地**：value=UUID+线程ID（UUID 区分 JVM、线程ID 区分 JVM 内线程）；释放走 Lua（`KEYS[1]`=锁 key、`ARGV[1]`=线程标识），比对一致才 DEL
- **集群失效的暴露条件**：必须**并发**压测（两个 JVM 同时查重都见"无单"）；串行双击第 2 次会读到已提交订单被正常拒绝，掩盖问题
- **压测脚本归档**：`backend/scripts/jmeter-seckill-oversell.jmx`（单机超卖）、`jmeter-seckill-cluster.jmx`（集群轮询）

### 9.6 Redisson 分布式锁（2026-10-10 需求 13 ✅）——面试文档

**项目里干了什么**：引入 Redisson 3.27.2 替换手写 SimpleRedisLock 作为秒杀消费端幂等兜底锁，并记录了手写锁四大缺陷与 Redisson 的对应解法。

**是什么**：一个以 Redis 为底座的 Java 客户端 + 分布式数据结构工具集（RLock 可重入锁 / RSemaphore / RBloomFilter…），核心价值是把"分布式锁的工程细节"（续期、重试、重入）做成了开箱即用的能力。

**为什么（手写 SETNX 锁的四大缺陷 → Redisson 解法）**：

| 手写锁缺陷 | 场景还原 | Redisson 解法 |
|---|---|---|
| 不可重入 | 线程拿锁后在嵌套方法里再次抢同一把锁，死锁自己 | Hash 结构：field=`UUID:threadId`，value=重入次数，同标识 HINCRBY 计数 +1/-1，减到 0 才 DEL |
| 不可重试 | 抢锁失败立即返回，用户体验差 | 基于 Redis **发布订阅**：持锁线程 unlock 时 publish 释放消息，等待线程订阅到再重试（非自旋空转） |
| 锁超时失效 | 业务耗时 > 锁 TTL，锁提前过期，互斥失效 | **看门狗 WatchDog**：无参 `tryLock()` 默认锁 30s，后台每 10s（TTL/3）检查持有者还活着就续期回 30s；业务结束 unlock 后不再续 |
| 主从锁丢失 | 主节点写入锁后未同步给从即宕机，从晋升后锁"消失"，第二个客户端加锁成功，互斥失效 | 理论解法 Redlock 红锁（向多个**独立**主节点过半加锁才算成功），但存在争议（时钟漂移/故障恢复语义），本项目未引入，面试讲得出取舍即可 |

**怎么干（代码实现）**：

```java
// 1. 依赖：org.redisson:redisson:3.27.2（笔记写 3.13.6 与 JDK21 不兼容，已升）
// 2. 配置：RedissonConfig 手动 new Config()（不用 starter，与 Spring Cache 场景解耦）
RLock lock = redissonClient.getLock("lock:order:" + userId);
boolean isLock = lock.tryLock();   // 无参 = 开启看门狗续期
if (!isLock) return false;         // 抢锁失败快速返回
try {
    selfProxy.createVoucherOrder(order);  // 事务方法走代理
} finally {
    lock.unlock();                 // 看门狗随业务结束停止续期
}
```

**原理速记（面试口诀）**：Hash 记标识可重入，Semaphore 订阅做重试，WatchDog 续期防超时，红锁防主从切换丢锁但有争议。

**适用场景**：锁内业务耗时不可预估（看门狗兜底）、需要重入（递归/嵌套加锁）、JVM 集群环境。不适用/不必要：极短临界区（原子 Lua 更轻，见 9.7——本项目资格判断已改用 Lua，Redisson 退居消费端幂等兜底）。

### 9.7 Redis 秒杀资格判断：Lua 原子化（2026-10-10 需求 14 ✅）——面试文档

**项目里干了什么**：新增秒杀券时把库存预热到 Redis（`seckill:stock:{voucherId}`），抢购时用一段 Lua 在 Redis 端原子完成「判库存 → 判一人一单 → 预扣 → 记录用户」，**取代了分布式锁**。

**为什么不再需要锁**：上一版用分布式锁串行化"查重+下单"，是因为判断与记录之间存在间隙；现在 `sismember + sadd + incrby` 在同一 Lua 脚本内原子执行——同一用户的并发请求，第一个 `sadd` 后，第二个的 `sismember` 必然看到它直接返回 2。**锁的使命（消除间隙）被更轻量的原子脚本取代**，还省去了加锁/释放/续期的全部网络往返。

**怎么干（代码实现）**：`resources/lua/seckill.lua`，返回 0=通过 / 1=库存不足 / 2=重复下单；`VoucherServiceImpl.addSeckillVoucher` 事务内 `set` 库存缓存（Redis 写失败随事务回滚）；Java 侧 `execute(SECKILL_SCRIPT, keys, args)` 一次往返拿到判定结果。

**适用场景**：判断+变更可以打包进 Redis 的短临界区（资格判断、限流计数）。不适用：临界区内含数据库写事务（Lua 里不能碰 MySQL——所以"预扣在 Redis、真扣在 DB"两段式，见 9.8）。

### 9.8 异步秒杀演进：阻塞队列 → Redis Stream（2026-10-10 需求 15/16 ✅）——面试文档

**项目里干了什么**：秒杀请求从"同步写库"演进为"Lua 判资格 + 消息队列削峰 + 后台消费落库"，队列从 JVM 内 ArrayBlockingQueue 演进到 Redis Stream 消费者组。

**演进链与驱动因素（面试主叙线）**：

| 版本 | 方案 | 致命缺陷 → 驱动演进 |
|---|---|---|
| v1 同步 | 锁 + 直接写库 | 高并发下所有请求串行等 DB，响应慢、DB 扛峰值 |
| v2 阻塞队列 | Lua 通过后 `offer` 进 JVM 内 ArrayBlockingQueue(1024)，后台线程消费落库 | ① **JVM 内存限制**：队列容量上限受堆约束，满后只能拒绝；② **宕机丢消息**：预扣已发生、订单未落库，Redis 与 DB 永久不一致，用户"抢到了却查无单" |
| v3 Stream（当前） | Lua 末尾 `XADD` 进 stream.orders；消费者组 g1 后台 `XREADGROUP` 消费 | 消息持久化在 Redis（宕机不丢）+ XACK 确认机制（至少消费一次）+ pending-list 回溯重试 |

**怎么干（代码实现）**：

```
抢购线程：Lua（判资格+预扣+SADD+XADD 一气呵成）→ 立即返回 orderId
消费线程：@PostConstruct 幂等建组 → 启动先清一次 pending（补上次宕机遗留）
         → 循环 XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS ... >
         → BeanUtil 还原订单（注意：消息字段 orderId ≠ 实体字段 id，需手动 setId）
         → Redisson 锁（幂等兜底）+ DB查重 + 乐观锁真扣 + 落库
         → 成功才 XACK；失败留 pending，异常时进 handlePendingMessages 以 "0" 重读
```

**关键机制**：`">"` 读新消息 / `"0"` 读 pending；双实例共用同组 g1 同名 c1，消息恰好投递一次（谁先 XREADGROUP 谁认领）；BLOCK 2000 防空转；毒消息场景生产上应加重试上限 + 死信队列。

**实证（2026-10-10）**：券 13 首购即时返回 orderId，消费线程 3s 内落库同 id 订单、XACK 后 XPENDING=0；人为踩坑（消息字段名 orderId 与实体 id 不匹配）导致插入失败，消息**不丢不弃**留在 pending，修复重启后被补处理落库——"至少消费一次"完整闭环；集群终验（nginx 轮询 8081/8082，JMeter 200 并发同用户）：订单恰好 1、DB 库存 98→97、Redis 预扣 97、无锁残留。

**适用场景**：秒杀/抢票/点赞计数等"判断在 Redis、落库可异步"的削峰场景。不适用：需要强一致即时感知结果的交易（如支付扣款本身）；消息量大到需要专业 MQ 的场景（Stream 是轻量队列，超大规模选 Kafka/RocketMQ，但多一套中间件成本）。
